Research project · UCSC

Route coding tasks to the cheapest model that can solve them

Hecate is a lightweight routing framework for LLM-assisted software engineering. Instead of guessing difficulty from text alone, routing labels are execution-grounded: patches are generated, applied, and tested — the cheapest tier that passes defines the label.

Core idea

Labels from execution, not intuition

Most routers predict escalation from issue text or embeddings alone. Hecate treats routing as an empirical question: for each task, several models attempt a fix under an identical scaffold. Only outcomes that survive test execution count.

A small encoder (DistilBERT-class) learns to predict whether a task can stay on a cheap model or must escalate — preserving success rates while cutting expensive large-model calls.

Five-stage pipeline

From patch generation to evaluation

  1. 01

    Patch generation

    Collect one attempted fix per (task, model) pair under a shared scaffold. Stage 1 does not execute tests — it builds the counterfactual matrix.

    In progress
  2. 02

    Execution

    Apply patches in a Docker harness and run project tests to learn which model tiers actually resolve each task.

    Planned
  3. 03

    Label construction

    Derive routing labels from execution outcomes — binary escalate vs. multiclass cheapest-resolver (deferred until pilot data).

    Planned
  4. 04

    Router training

    Fine-tune the encoder router on execution-grounded labels, then adapt to undergraduate SDLC course usage data.

    Planned
  5. 05

    Evaluation

    Compare Hecate against always-small, always-large, and heuristic baselines on cost and task success.

Method

Invariants that protect label validity

Shared scaffold

Identical issue text, file context, and prompt for every model. Only the model slug varies.

Single-shot (v1)

One prompt → one patch. No multi-turn agent loop in the first release.

Oracle context

Target files from gold patches (oracle) or BM25 — same retrieval method for all models.

Full counterfactual matrix

Persist raw outcomes for every (task, model) pair; never collapse away per-pair detail.

Rich storage

Record patch + metadata now; defer binary vs. multiclass label scheme to Stage 3.

Reproducibility

Every run writes a manifest: config snapshot, model slugs, timestamp, git commit, total cost.
